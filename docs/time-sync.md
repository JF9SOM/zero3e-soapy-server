# 時刻同期の検討 — 2026-11-26

## 前提
- Mac 直結（192.168.50.x）ではインターネット（NTP）に出られない。`systemd-timesyncd` は有効だがサーバーに届かず `Packet count: 0`、`System clock synchronized: no`
- SoapyRemote のストリームにタイムスタンプはない（`SoapySDRUtil --probe` で `Timestamps: NO`）。FBSAT59 は Mac の時刻を使う → ZERO 3E の時刻が影響するのはジャーナル・温度ログの日時のみ

## 測定結果（Mac を基準）
1. 再起動後（RTC は Mac と 1〜2 秒差で正しかった）: システム時刻が **110 秒遅れ**。61 秒間は 110 秒のまま変化せず（時計の進む速さは合っている）
   - kernel は RTC から時刻を設定（`setting system clock to 2026-11-26T07:32:45 UTC`）したが、その後 `fake-hwclock` が保存値（`/etc/fake-hwclock.data` = 07:31:02 UTC）を書き戻したと推測（保存値・起動時刻の数値が一致。Armbian の fake-hwclock が RTC より古い保存値で上書きする挙動は、設定ファイル等では未確認）
2. **電源断テスト**（`sudo poweroff` → USB-C を約 3 分抜く → 再接続、インターネット共有オフ）:
   - RTC: `2017-08-04 09:00:33`（= rk808 RTC の初期値付近）→ **RTC は電源断で時刻を保持しない**（電池バックアップなし。基板に RTC 電池用の端子があるか・電池を付けられるかは未確認）
   - システム時刻: fake-hwclock の保存値（シャットダウン時の時刻）から再開し、Mac より **335 秒遅れ**（シャットダウン前の遅れ約 110 秒＋停止時間約 225 秒）
   - 結論: 電源を切った時間の分だけ遅れる（無停電でも再起動で遅れる）。インターネット/NTP が使えるまで戻らない

## 選択肢
1. 現状のまま（ログ時刻が数分〜電源断時間ぶんずれる）
2. Mac を NTP サーバーにする（Homebrew の chrony 等を Mac で動かし `allow 192.168.50.0/24`、ZERO 3E の `timesyncd` を `NTP=192.168.50.1` に。macOS 標準の NTP サーバー機能は無いと考える・要確認）。Mac 常駐ソフトが増える
3. Mac から SSH で時刻を送る（ZERO 3E 側で `date`/`timedatectl` を NOPASSWD sudo で許可する必要あり。セキュリティ設定の変更を伴う）
4. メンテナンス時のインターネット共有（`apt upgrade` 等）で timesyncd に同期させる（共有オンで DHCP 取得後に自動同期する見込み・未確認）
5. RTC 電池を付ける（ハード側。対応・仕様は要確認）
- 判断: 現時点では実害が小さいため 1 か 4 で十分。時刻の正確さが必要になった場合は 2 を検討

## 決定（2026-11-26）
- **現状のまま運用する**（選択肢 1）。ZERO 3E の時刻は電源断・再起動のたびに遅れるが、影響はジャーナル・温度ログの日時のみ
- ログを見るときは、時刻がずれている前提で読む（Mac 基準で数分〜電源断時間ぶん遅れ）。メンテナンスでインターネット共有をオンにしたときは timesyncd が同期する見込み（未検証）
- 正確さが必要になったら、選択肢 2（Mac を NTP サーバーにする）を検討
